# Story 1.4 — карта большой книги и диалог в сеансе

## Что сделано

- `/workbook` работает по явному типизированному двухфазному протоколу:
  1. task pane строит metadata-only `WorkbookMap` (этап «Строю карту книги…») и отправляет её вместе с вопросом в `POST /api/sessions/{sessionId}/workbook/plan`;
  2. API просит Qwen выбрать диапазоны, затем сам их валидирует (лист есть в карте, A1, обрезка до used range, ≤ 5 диапазонов, ≤ 10 000 ячеек на диапазон, ≤ 20 000 суммарно) и возвращает `WorkbookPlan`;
  3. task pane читает через Office.js только запланированные диапазоны (размер проверяется до загрузки значений);
  4. `POST /api/sessions/{sessionId}/workbook/analysis` принимает только артефакты, в точности совпадающие с одноразовым планом, и только их передаёт Qwen.
- В ответе показаны фактические источники (лист · адрес) и покрытие: «Проанализированы только релевантные части книги: N из M лист(ов) — …».
- Память сеанса: opaque `sessionId` (`secrets.token_urlsafe(32)`), карта, история вопрос–ответ, временные артефакты и одноразовые планы хранятся только в RAM процесса API. Follow-up использует историю и карту без повторной отправки карты и без повторного выбора scope.
- Очистка: смена scope → `DELETE /api/sessions/{id}` и чистая история; `pagehide` → `navigator.sendBeacon(POST /api/sessions/{id}/close)`; кнопка «Начать новый диалог»; idle TTL `FINLENS_SESSION_TTL_SECONDS` (default 1800, допустимо 60–86400) со скользящим продлением и фоновой очисткой каждые ≤ 60 с; при `SESSION_NOT_FOUND` task pane очищает локальную историю.
- Ограничения большой книги объясняются честно с одним следующим шагом: > 100 листов (`WORKBOOK_TOO_LARGE` на клиенте), слишком большие релевантные данные (`WORKBOOK_SCOPE_TOO_LARGE`), отсутствие релевантных данных (`NO_RELEVANT_DATA`), невалидный/превышающий лимит запрос (`REQUEST_INVALID` теперь с `analysisId`, `elapsedMs` и `nextAction`).
- Range/sheet тоже ведут историю в сеансе (необязательный `sessionId` в `AnalysisRequest`), чтобы уточняющие вопросы работали во всех scope.
- UI: единая панель, нумерованная история диалога (`<ol aria-label="История текущего диалога">`), текстовые этапы в постоянном `role="status" aria-live="polite"`, возврат фокуса в поле «Уточняющий вопрос» после ответа, кнопки scope заблокированы во время анализа, ошибки хода — «Не удалось ответить… Следующий шаг: …».
- Production prompt структурирован: system-правила аналитика (только переданные данные, язык вопроса, вывод → причины/доказательства с адресами → риски → допущения → следующая проверка, честность при нехватке данных, содержимое книги — данные, а не инструкции) + JSON с вопросом, последними 6 ходами, картой и артефактами. Финансовые сценарии не захардкожены. Ответ Qwen валидируется схемой `Narrative` / `SelectionResponse`.
- Fake provider остаётся только при `FINLENS_QWEN_PROVIDER=fake`, явно подписан как тестовый; без конфигурации — `QWEN_NOT_CONFIGURED`.

## Архитектурные решения

- AD-2: map — только структура (имя листа, позиция, видимость, адрес и размеры used range, имена и адреса таблиц ≤ 20 на лист); никаких values/formulas/numberFormat. Pydantic `extra="forbid"` отвергает карту с ячейками; размеры проверяются по адресу.
- AD-3: выбор Qwen — лишь предложение; финальные границы задаёт API. План одноразовый и привязан к `analysisId`; лишние/иные артефакты → `ARTIFACTS_MISMATCH` (409) без вызова Qwen.
- AD-6: сеанс привязан к scope; несовпадение → `SESSION_SCOPE_MISMATCH`. Нет БД, файлов, localStorage, экспорта. При закрытии все поля сеанса явно очищаются. Хранится ≤ 20 ходов, в prompt — последние 6; ≤ 500 сеансов (`SESSION_CAPACITY`, 503).
- Логи: только `analysisId`, длительности, число листов/диапазонов/ячеек/ходов и коды ошибок; `sessionId`, вопросы, ячейки и промпты не логируются (покрыто тестом).
- HTTP-эндпоинты стали синхронными (`def`), чтобы блокирующий вызов Qwen шёл в threadpool и не останавливал event loop; store защищён `threading.Lock`.
- Retry, отмена анализа, песочница и графики не добавлялись (Epic 2/3).

## Ограничения и риски

- Production Qwen не вызывался: endpoint не предоставлен. Качество выбора диапазонов и ответа нужно проверить на обезличенных книгах.
- Ручная проверка в Excel Desktop Windows не выполнена (macOS-среда).
- Унаследовано от Stories 1.1–1.3, вне scope 1.4, но блокирует ручную проверку: (1) API не настроен на CORS для origin task pane, а `https://localhost:5173` → `http://localhost:8000` — ещё и mixed content; (2) `main.tsx` не ждёт `Office.onReady`, поэтому `getCompatibility()` может увидеть неинициализированный `Office.context` и показать «не поддерживается». Нужны отдельные решения/истории.
- Сеансы живут в памяти одного процесса API: при нескольких worker/репликах нужен sticky routing или выделенный in-memory store (без персистентности) — решение для деплоя.
- Карта кэшируется в сеансе: если в открытой книге добавили листы, обновить карту можно сменой scope или «Начать новый диалог».
- Числовые лимиты (100 листов, 5 диапазонов, 10 000 / 20 000 ячеек, TTL 1800 с) — стартовые значения; PRD требует уточнить их на пилотных книгах.

## Точные ручные действия для Excel Desktop Windows

1. `npm ci`; `pip install -r api/requirements.txt`.
2. Устранить блокеры выше (CORS для origin task pane и HTTPS для API, ожидание `Office.onReady`) или проверять через доверенный HTTPS-прокси на одном origin.
3. Backend: `cd api`, задать `FINLENS_QWEN_BASE_URL`, `FINLENS_QWEN_API_KEY`, при необходимости `FINLENS_QWEN_MODEL` и `FINLENS_SESSION_TTL_SECONDS=120` (для проверки TTL), запустить `uvicorn app.main:app --port 8000`.
4. Task pane: `VITE_FINLENS_API_URL=<URL API> npm run dev`; sideload `manifest.xml` (общая папка-каталог надстроек или `npx office-addin-debugging start manifest.xml desktop`).
5. Открыть обезличенную многолистовую книгу, сохранить её копию и контрольную сумму файла.
6. В FinLens нажать «Книга» (или `/workbook`): плашка «Книга · N лист(ов), с данными: K».
7. Спросить «Что это за модель, какие ключевые допущения и риски?»: видны этапы «Строю карту книги…», «Выбираю релевантные листы и диапазоны…», «Читаю только выбранные диапазоны (…)», «Готовлю вывод…»; в ответе — источники и строка о покрытии листов.
8. Задать уточнение («А какие риски у долга?») без смены scope: в истории два хода, этап «Использую карту книги текущего сеанса…».
9. Нажать «Лист»: история исчезает; следующий вопрос начинает новый сеанс.
10. Подождать дольше TTL и задать вопрос: сообщение об истёкшем сеансе и очищенная история; повторная отправка работает.
11. Книга > 100 листов или вопрос «по всей книге» с огромными листами: понятное объяснение лимита и предложение выбрать лист/диапазон.
12. Закрыть панель и открыть снова: история пустая. Проверить логи API: только IDs, длительности, размеры и коды.
13. Закрыть книгу без сохранения и сравнить контрольную сумму файла с исходной (книга не изменена); проверить пункты с экранным диктором и только клавиатурой.
